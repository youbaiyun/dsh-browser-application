# Permission justifications for the store dashboard

The dashboard asks for a written reason once per declared permission. The text below is what a
reviewer reads, so it is written for them and it must stay true to the manifest: **every
permission listed here must be one the build actually declares**, and a permission the build
does *not* declare must not appear. Check it against `extension/dist-store/manifest.json`
before pasting, and use English — the review team reads English, even when the dashboard is
displayed in Chinese.

## What the current build declares

```
permissions        : sidePanel, storage, tabs, scripting, webNavigation, alarms, notifications
host_permissions   : http://*/*, https://*/*
content_scripts    : http://*/*, https://*/*
```

**Do not mention `activeTab`.** It was declared and unused in an earlier build, and was removed.
Explaining a permission you do not request invites a question you cannot answer.

## Single purpose

```
Operate the browser tab the user selects, on behalf of the dsh desktop app running on the same machine.
```

## sidePanel

```
The side panel is this extension's entire user interface: the conversation with the model, the approval cards and the settings all live in it. There is no popup and no separate tab, so it is the minimum surface that can hold them. The user opens it and keeps it open while browsing, because the page beside it is the page being operated.
```

## storage

```
Remembers, locally, only what the extension needs to work across restarts: the loopback address and token of the desktop app, the user's preferences (page-content sharing mode, tab-switch behaviour, reading width, vision tier), and a memo of image descriptions it has already produced so the same image is not fetched and described twice. The memo holds at most 200 entries for 24 hours. Nothing is synced and nothing is uploaded.
```

## tabs

```
Lists the open tabs so the user can choose which page the tools operate on, keeps the tools bound to that tab (including across a manual tab switch, when the user has chosen that behaviour), and opens a tab when the user's own request needs one. Only tab titles and URLs are read, for the picker; browsing history is not read or stored.
```

## scripting

```
Injects the page reader and the action executor into the tab the user selected. Both have to run on the live page: the reader turns it into structured text plus a numbered list of controls, and the executor performs the click, keystroke or scroll the model asked for. Injection is limited to the selected tab.
```

## webNavigation

```
Detects when a navigation in the selected tab has finished, so the next page read sees the settled document instead of one still loading. It is used purely as a completion signal; no navigation history is recorded or transmitted.
```

## alarms

```
Keeps the loopback connection to the desktop app alive across MV3 service-worker suspension. The browser stops an idle worker, and the desktop app is a client that must not be dropped in the middle of a task.
```

## notifications

```
Raises an approval request as a system notification when no side panel is open, so a decision the model is waiting on is not silently lost. Notifications are used only for this extension's own approval flow.
```

## Host permission (`http://*/*`, `https://*/*`)

This is the field most likely to draw a human reviewer, and the dashboard warns that host
permissions can mean a deeper review and a later release. Give the whole argument rather than a
summary, and do not narrow the pattern to shorten the queue: the page the user is looking at is
not known when the manifest is written, so any fixed domain list would break the feature
everywhere else.

```
The extension operates the page the user is looking at, and that page is not known when the manifest is written — the user may be on any site. No narrower pattern would work: a fixed domain list would break the feature everywhere else.

What limits it: the content script only reads and acts on the tab the user explicitly selects; reading and acting are separate operations; passwords and payment-card values are replaced in place in the snapshot and never leave the page; page text is labelled as untrusted input so a page cannot issue instructions that look like the user's. Approval can also be turned on, and per-site trust is available.
```

## Data usage disclosure

On Chrome, tick **only** website content:

| Category | Selection |
|---|---|
| Personally identifiable information | **not collected** |
| Authentication information | **not collected** (the bridge token is generated by the desktop app and stored locally by the browser) |
| Web history | **not collected** |
| Website content | **read**, at the user's direction, and sent to the model the user configured. This is the extension's function |
| User activity | **not collected** |
| Location | **not collected** |

Where the form then asks what each category is used for, select only **app functionality**; leave
analytics and personalisation unselected.

## The final confirmation

Publishing is blocked until the **Privacy practices** tab's closing declaration is ticked —
"your data usage complies with the Chrome Web Store Developer Program Policies". The dashboard
reports this as *无法发布 / You must confirm your data usage…*, which reads like a content error
but is only an unticked box. Tick it, **save the draft**, and submit again.
